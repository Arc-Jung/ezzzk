# 멀티뷰 자동 음량 디버깅

2026-11-05, Chromium에서 확장을 로드해 확인했다.

## 발견한 문제

### 갑자기 큰 소리가 나올 때 출력 초과

기존 자동 보정은 250ms마다 최근 파형을 측정한다. 작은 소리를 증폭한 직후 큰 소리가 나오면, 다음 측정과 점진적인 게인 감소를 기다리는 동안 출력이 최대치 1을 넘을 수 있었다. 일정 진폭만 사용하는 기존 검증은 이 구간을 놓쳤다.

실제 공개 방송의 측정 중 큰 피크를 관찰한 뒤, 진폭 0.005가 4초간 이어지고 0.8로 0.3초간 급변하는 WAV로 재현했다. 수정 전 최대 출력은 **4.9901**이었다.

자동 보정 뒤에 오디오 렌더 스레드에서 작동하는 피크 제한을 추가했다. `DynamicsCompressorNode`의 문턱은 0dB, knee 0, attack 0, release 0.05초이며 ON일 때 ratio 20, OFF일 때 ratio 1이다. 앞뒤의 2배·0.5배 게인은 평상시 상쇄되고, 0.5를 넘는 큰 피크에 압축을 적용한다. 문턱을 낮추는 방식에서 생기는 브라우저의 메이크업 증폭이 평상시 목표 음량을 바꾸지 않도록 구성했다. 기존 사용자 컴프레서와는 별도 노드다.

이 제한은 모든 파형에 대한 수학적인 하드 클램프가 아니다. 아래 표는 실제 출력 파형을 읽은 회귀 시험 결과다. 브라우저의 오디오 처리 지연도 추가될 수 있다.

### 수동 볼륨 중복 적용과 증폭값 잔류

50%에서 `video.volume=0.5`와 수동 Web Audio 게인 0.5가 함께 적용되던 경로가 있었다. 실제 소리는 25%가 되어 자동 보정 계산과 사용자 표시가 어긋났다. 100% 이하는 미디어 요소가 담당하고, Web Audio 수동 게인은 1로 유지하도록 수정했다.

또 컴프레서를 끈 상태에서 150% 증폭을 사용하다 100% 이하로 내리면 기존 그래프를 갱신하지 않아 증폭값이 남을 수 있었다. 이미 생성된 그래프를 조회해 갱신하고, 치지직 기본 슬라이더의 `volumechange`에서도 같은 처리를 적용한다.

## 실제 브라우저 회귀 시험

| 조건 | 결과 |
| --- | ---: |
| 자동 음량 OFF, 진폭이 다른 4개 신호 | 출력 차이 18.07dB |
| 자동 음량 ON, 같은 수동 볼륨 | 출력 차이 0.054dB |
| 급격한 진폭 변화, 수정 전 | 최대 피크 4.9901 |
| 같은 진폭 변화, 수정 후 | 최대 피크 0.5992 |
| 같은 진폭 변화, 수동 200% 증폭 | 최대 피크 0.7925 |
| 기존 컴프레서 ON, 수동 50% | RMS 약 0.040, 슬롯 간 차이 0.042dB |

피크 시험은 4096개 샘플을 10ms마다 읽어 6초간 600회 측정했다. 200%에서 100% 복귀, 일시정지 후 재개, 영상 요소 교체, 무음 후 복구, 반복 토글 시 소스 재사용, OFF 시 원본 출력·기존 컴프레서 유지도 확인했다. 브라우저 자동재생 정책은 사용자 동작을 요구하도록 설정했다. 시험 소리는 시스템 출력에서 음소거했고 오디오 파일을 녹음하거나 외부로 전송하지 않았다.

수동 음량 차이는 의도적으로 유지한다. 서로 다른 수동 볼륨이나 음소거를 자동으로 되돌리지 않는다. 위 수렴 수치는 같은 수동 볼륨의 합성 신호에 해당하며, 음악·대화가 계속 바뀌는 실방송의 체감 음량을 완전히 같게 한다는 뜻은 아니다.

추가 실방송 확인에서는 4개 슬롯을 열어 3개 슬롯의 보정 출력을 확인했다. 나머지 슬롯은 영상 준비를 확인하지 못해 측정에서 제외했다. 12회 표본에서 확인한 출력 피크는 최대 0.555였으며, 연속 피크 제한이나 4개 실방송 전체의 동작을 증명하는 시험으로 해석하지 않는다. 정량 비교는 재현 가능한 4개 WAV 시험을 기준으로 한다.
